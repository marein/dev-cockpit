# e2e runners

Executable Playwright runners, one file per feature. Each script carries its own
what and why in a header comment (purpose, routes, custom elements, gotchas) and its
checks as descriptive names, so this is the single source of truth (no separate
markdown spec). Shared helpers are in `lib.js`. Mobile and desktop divergence is
covered inside the feature that owns it, mainly `terminal.js` and `coders.js`.

The scripts drive throwaway instances only, create their own scratch project plus
sessions and shells, and delete everything they create. Never attach to a session
you did not create. Destructive selectors (resume, delete, stop) on shared pages
like /projects MUST be scoped to the runner's own project row
(`#project-<scratch>`); the page lists the real projects' stored coders
too, and an unscoped `.first()` deletes someone's session store.

## Run

Build the runner image once (Playwright base plus a global `playwright-core`, see
`Dockerfile`), then a run needs no install and no `node_modules`:

```bash
docker build -t dc-e2e:1.60.0 - < tests/e2e/Dockerfile   # once
docker run --rm --network host [-e BASE_URL=...] [-e ENGINE=...] \
  -v "$PWD/tests/e2e":/work -w /work dc-e2e:1.60.0 node <feature>.js
```

`BASE_URL` defaults to `https://localhost:3010`. `ENGINE` defaults to `chromium`;
set `webkit` or `chromium,webkit` for the cross-browser (Chrome plus Safari) pass.
The only dependency is `playwright-core`, baked into the image (browser drivers need
it; there is no stdlib equivalent that also covers WebKit/Safari).

## Instances a full run needs

Throwaway instances per the shared setup, each with its own `--state-dir` and cookie
name. `--provider` is deprecated and ignored, every instance serves all coders whose
CLI is installed on the host. Most scripts run against the instance on `:3010`
(cookie `tc_session`), including `coder-claude.js` and `multi-coder.js`.
Extra instances:

- one on `:3012` started with `DEV_COCKPIT_UPDATE_API_URL` pointing at a stub
  returning a GitHub shaped `v999.0.0` release whose asset is this tree built
  with `-ldflags "-X main.version=999.0.0"`, packaged as
  `dev-cockpit_v999.0.0_linux_amd64.tar.gz` (tar.gz with a file named `dev-cockpit`)
  plus `dev-cockpit_v999.0.0_checksums.txt` (`<sha256>  <asset name>`), for
  `update.js MODE=available`. The env var reaches only a dev build, one whose
  `main.version` stayed `dev`: a release build ignores it and reads the feed
  URL baked in at build time, so the serving instance must be a plain dev
  build. The `999.0.0` asset binary is a release build by that rule and
  ignores the env var after the swap, which the runner tolerates, it only
  reads `current` from the re-execed instance. The release body has to carry
  the words `Stub release`, the changelog check reads the notes out of the
  dialog and matches them against `/Stub release/i`. The apply test asserts
  that the instance re-execs as `999.0.0`, so the version must really be baked
  in. Apply swaps the binary in place, the instance must run its own copy,
  never the repo build.
- one on `:3013` with the stub URL returning `[]`, for `update.js MODE=uptodate`.
- one on `:3017` for `update.js MODE=gitlab`: the same shape as `:3012`, but
  the instance binary is built with `-ldflags "-X main.updateFeedFormat=gitlab"` (and
  no `-X main.version`, it has to stay a dev build for the env var) and the
  stub answers the GitLab releases JSON instead: an array of objects with
  `tag_name`, `name`, `description` (the notes, carrying `Stub release`),
  `released_at`, `upcoming_release` and `assets.links[]` entries with `name`
  and `direct_asset_url` pointing at the same `v999.0.0` archive and checksums
  files.
- `assistant.js` and `wake.js` need their own instance with `tests/e2e/fakes`
  ahead of the real CLIs on `PATH` and `HOME` pointing at a scratch directory.
  Only those two runners belong on it: the fakes never persist an interactive
  session, so the terminal driven runners (quicknav, frontend, terminal) fail
  there for reasons that have nothing to do with the app. The fakes speak
  the documented claude and copilot machine protocols, persist a minimal
  provider session so the cockpit can resume it, and never spend a model
  request. Prompts steer them: `MAGIC` (fixed answer), `SLOW` (a turn that
  keeps running), `FAIL` (fails once per session, so a retry recovers),
  `MARKDOWN` (markup plus an injection attempt), `TOOL` (a tool signal), `CONTEXT_HIGH` (a turn reporting a nearly full context window; both fakes otherwise report 68 percent of it, and a check reports a number of its own so a leak into the conversation's ring is visible), `PAUSE_CHAT` (claude only: half the answer, twelve silent seconds, the rest).

  ```bash
  env -u TMUX TMUX_TMPDIR=/tmp/dcchat-tmux HOME=/tmp/dcchat-home \
    PATH="$PWD/tests/e2e/fakes:/usr/local/bin:/usr/bin:/bin" \
    ./dev-cockpit serve --addr 0.0.0.0:3014 --state-dir /tmp/dcchat-state ...
  ```
- `backup.js` needs its instance started with `HOME` pointing at a scratch
  directory. The backup import writes into the state dir and `$HOME`, so an
  instance with the real home must never serve this runner, even though the
  checks only select the settings section and keep the restart checkbox off.
- `editor-git.js` commits through the app, so the `HOME` its instance runs
  with needs a git identity (`user.name`, `user.email`). Without one git
  refuses every commit the panel sends, which is exactly what the runner
  reads as a failure in the five commit checks; the shell driven commits in
  the same runner carry their identity on the command line and pass anyway. That
  `HOME` must not pin `init.defaultBranch` either: the runner builds its
  repository with a plain `git init` and the clone check waits for the branch
  git names by default, so an override times that one check out and says
  nothing about the clone.
- `git-proxy.js` starts the real `dev-cockpit git` as a child process, so its
  instance needs a scratch directory holding everything the CLI has to reach.
  It must be mounted **at its own host path** (and `AUX_DIR` set to it), not
  at some `/aux`: the CLI sends its raw working directory and the server runs
  git in exactly that directory, so a container-only path names nothing on the
  host and every call fails with `fork/exec: no such file or directory`. The
  scratch holds: `bin/dev-cockpit` (a copy, never the
  repo build), the instance's `--state-dir` (which is where the local API
  socket lives, so the CLI inside the container talks to the instance outside
  it) and its `--projects-dir`. `HOME` points at `aux/home` and needs a git
  identity like `editor-git.js`'s. The projects dir holds one project
  (`gitproxy`, override with `GIT_PROXY_PROJECT`) that is a repository with a
  commit to push and an ssh stand-in wired through `core.sshCommand` plus a
  remote URL nothing can reach, the same shape `editor-git.js` builds:

  ```bash
  SCRATCH=/tmp/dcgitproxy   # bin/ state/ projects/ home/
  cp ./dev-cockpit $SCRATCH/bin/dev-cockpit

    $SCRATCH/bin/dev-cockpit serve --addr 0.0.0.0:3016 \
    --state-dir $SCRATCH/state --projects-dir $SCRATCH/projects \
    --session-cookie-name gp_session ...
  docker run --rm --network host -e BASE_URL=https://localhost:3016 -e AUX_DIR=$SCRATCH \
    -v "$PWD/tests/e2e":/work -v $SCRATCH:$SCRATCH -w /work dc-e2e:1.60.0 node git-proxy.js
  ```

  A check that throws while a question stands would leave the push waiting, so
  the runner answers the dialog in a `finally`. The bridge itself is not the
  hazard it once was: the server ends a proxied question when the caller goes
  away (`endWhenCallerGone`), so a killed CLI child frees the project instead
  of holding it until the question times out.
- `editor-lsp.js` needs its instance to carry the deterministic fake language
  server first on `PATH` under the name `gopls`: a directory holding an
  executable `gopls` wrapper that execs `python3 <repo>/tests/e2e/fake-lsp.py`,
  prepended to the instance's `PATH`. The same directory holds an executable
  fake `docker`: `image inspect` always fails, `build` sleeps three seconds,
  `run` execs the fake server (walking the run's options, `-w` as its
  working directory and every `-e` into its environment, which is how the
  fake server learns the bound module cache; `--pull=*` is skipped like the
  other flags), a `run` carrying
  `--entrypoint cat` prints a fixed Go source for a path under
  `/usr/local/go/src/` and fails for anything else, which is how the read
  out of an image is answered, and everything else exits quietly. The build
  phase check picks the Docker option against it, so the preparing indicator
  is visible and deterministic with no daemon involved. Without the fakes
  the runner reaches whatever real tools the host has and the answers stop
  being deterministic.
  Only `gopls` needs a wrapper: the setup pins every language to the Docker
  pick so one stored shape covers the whole page, but the suite's projects
  hold Go files alone, so no other server is ever started.
  The instance should be fresh: the setup check reads the LSP selects and
  accepts only the Automatic default or its own earlier pin. The boot
  sweep is scoped by a label carrying the instance's own projects root,
  so a throwaway with a projects directory of its own never touches a
  live cockpit's servers or volumes, and the fake docker keeps this
  instance off the real daemon entirely.

- `docker.js` needs its instance to reach a Docker daemon plus the docker
  CLI, and a compose fixture prepared in the instance's projects dir before
  the run: a project named `dockere2e` (override via `-e DOCKER_PROJECT=...`)
  whose directory holds a compose file with one service `web` that logs
  something at startup (`nginx:alpine` does), publishes port `18088`
  (`ports: ["18088:80"]`) and carries the two labels the default link rule
  reads, `traefik.enable=true` and
  ``traefik.http.routers.dockere2e.rule=Host(`dockere2e.test`)`` (override the
  host via `-e DOCKER_LINK_HOST=...`), brought up with `docker compose up -d`
  from inside that directory, so the `working_dir` label matches. No proxy has
  to run and nothing resolves that host: only the label is read, the runner
  reads the menu entry and never follows the link. The image must be
  local, the compose up check waits no pull. The runner stops, starts and
  composes only that fixture and leaves the stack up; `docker compose down`
  afterwards is the host's cleanup. The delete check creates a scratch
  project with a stack of its own (same image, no published port), deletes
  it and takes the leftovers with it, so a failed run may leave one stopped
  `dcdel-*` stack behind.

Never save `/instructions` outside the runners' own flows, the instance writes the
real per-coder files in `$HOME` (the default coder is the first installed one).

Stop each instance by PID when done, never `pkill`.

## Notes

- `page.waitForFunction` does not await an async predicate: the returned
  promise is always truthy and the wait resolves at once, on both polling
  modes. A wait that has to fetch something polls from the Node side instead
  (an `evaluate` in a loop, see `waitNotify` in `docker.js`).
- Runs report a non-gating `cdn noise` count (the editor's CodeMirror packs
  throttled by their third-party CDN, plus WebKit's "due to access control
  checks" page error for the /events, /update/check and editor terminals
  fragment background requests a navigation aborts mid-flight); only
  app-origin console and page errors gate. Rationale and filters live in
  `lib.js` (`isCdnNoise`, `isWebkitAbortNoise`).
